## 0. 一页结论（给老板）

**能做，但先要把"做到什么程度、卖给谁、多久要"定清楚。**

1. **技术可行性高。** SIP 是成熟标准（RFC 3261 系列），Go 生态有可商用的开源协议栈（[sipgo](https://github.com/emiago/sipgo)，BSD-2）与媒体库（[Pion](https://github.com/pion)，MIT），足够支撑 50~500 分机、50~250 并发的企业级 SIP 服务器。Go 可交叉编译出 Windows / Linux / macOS / ARM 单文件程序，**客户现场零依赖**，正好解决 ZYCOO 这类"只能装 Linux、Docker 还要 host 网络"的交付痛点。
2. **工作量不小。** miniSIPServer 官方特性表约 50 项，覆盖注册、中继、前转、IVR、语音信箱、会议、队列、BLF、WebRTC、TLS/SRTP、IPv6 等。**从零到"功能基本对齐、可批量交付"约 30~36 人月**；只做报警/对讲行业所需的 MVP 约 10~12 人月。
3. **最大风险不在信令，在工程细节。** 媒体质量（抖动缓冲/转码/混音）、NAT 穿透、几十种话机与自家报警设备的兼容性、Windows/macOS 服务化与安装包、售后远程诊断——这些才是吃工期的部分。
4. **不建议直接套 FreeSWITCH / Asterisk 交付。** 功能现成、上市快，但体积大、依赖多、Windows/macOS 支持弱、许可证（GPL/MPL）对闭源销售不友好，且很难做到"客户双击安装就能用"。它们适合做过渡 Demo，或作为高端型号的后端。
5. **建议动作：** 先批 **2 周 PoC**——用真实报警设备 + 两款软电话，跑通"注册 → 呼叫 → 录音 → Web 面板 → 三平台安装包"，再决定是否投入 10 个月。

**一句话：这是一个 10~12 个月、3~4 人、百万级投入的产品级项目，不是三个月的外包活儿；但路径清晰、风险可控，且能沉淀成公司自己的通信底座。**

## 1. 背景与目标

### 1.1 现状与痛点

| 事项 | 现状 |
| --- | --- |
| 设备侧配置 | `sip_web` 已有 Vue3 + Element Plus 的 Web 配置界面，负责给报警/对讲设备下发 SIP 账号、服务器地址等参数 |
| 服务器侧 | 依赖第三方 SIP 服务器；客户现场环境不可控 |
| ZYCOO 尝试 | IP Audio Center 是 Asterisk + MySQL + Redis + Nginx 的重型 Linux 镜像（x86_64 ISO）；Docker 版 SIP 内核用 `network_mode: host`，在 macOS Docker Desktop 上实测不通；无法在客户随便一台 Windows 小主机/树莓派/云主机上交付 |
| 商业诉求 | 自主可控、可白标、可随设备搭售、不按客户端数量向第三方交授权费 |

### 1.2 目标

- **全平台**：Windows 10/11/Server、Linux（x86_64/arm64）、macOS（Intel/Apple Silicon）、树莓派、Docker、主流云主机。
- **Web 管理**：浏览器完成全部配置、监控、话单、录音、诊断，不依赖桌面 GUI。
- **功能对标**：覆盖 miniSIPServer 官方特性表（见附录 A），并做得更符合国内交付习惯。
- **行业增强**：一键报警、视频对讲、广播分区、与报警平台联动——这是第三方通用 PBX 不会做的部分。
- **交付体验**：单文件安装、服务自启、防火墙自动配置、一键升级、一键导出诊断包。

### 1.3 首期非目标

- 电信级集群、多租户、5000 路以上并发；
- 与 Kamailio/OpenSIPS 对标的运营商级软交换；
- 传真（T.38）、复杂呼叫中心（预测式外呼、质检）、计费对接——可后续扩展。

## 2. "所有功能"到底有多少

### 2.1 功能分层

官方特性表约 50 项，加上系统/运维能力，实际约 **60~70 个功能点**。按价值分五层：

| 层级 | 内容 | 工作量占比 | 说明 |
| --- | --- | --- | --- |
| L1 基础协议 | 注册、鉴权、UDP/TCP/TLS、NAT、SIP 中继、拨号规则、DNS | ~20% | 没有它什么都跑不起来，但相对标准化 |
| L2 呼叫业务 | 基本呼叫、前转、转移、代答、停泊、振铃组、一号多机 | ~25% | 客户日常真正用到的部分 |
| L3 增值业务 | IVR、语音信箱、会议、队列、BLF/Presence、IM、WebRTC | ~30% | 拉开差距，也最费工 |
| L4 运维安全 | Web 管理、CDR、录音、TLS/SRTP、黑白名单、诊断 | ~15% | 决定"能不能交付、好不好维护" |
| L5 行业增强 | 一键报警、视频对讲、广播分区、平台联动 | ~10% | 我们的护城河 |

### 2.2 看起来简单、实际很贵的 8 件事

1. **会议混音**：N 方混音、选听、DTMF 控制、音量归一化。
2. **IVR-XML**：可编程流程引擎（放音/收号/条件/转接/变量），还要配套调试工具。
3. **语音信箱**：留言录制、MWI 通知、Web 试听、保留/清理策略。
4. **WebRTC 网关**：ICE/DTLS/SRTP/SDP 协商、浏览器兼容、TURN 部署。
5. **编解码转码**：G.711 ↔ G.722 ↔ Opus，涉及性能、抖动缓冲与专利。
6. **Presence / BLF**：SUBSCRIBE/NOTIFY、dialog-info、几百分机状态风暴。
7. **TLS / SRTP 全链路**：证书签发/上传/续期、密钥协商、WSS。
8. **IPv6 双栈**：监听、SDP 选路、NAT64 场景，测试成本高。

> 结论：**"全部功能"不是一个版本能做齐的**。建议按"行业 MVP → 完整 PBX → 全功能对齐"三期推进，每期都能独立交付、独立卖。

## 3. 技术路线对比

| 路线 | 代表方案 | 上市速度 | 全平台 | 可控/白标 | 许可风险 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **A. Go 自研** | sipgo + Pion + Vue3 | 中（~10 个月） | ★★★★★ | ★★★★★ | 低（BSD/MIT） | **推荐** |
| B. FreeSWITCH 封装 | FS + 自研 Web + ESL | 快（3~4 个月） | ★★☆（Windows 弱） | ★★★☆ | 中（MPL 1.1，模块需注意） | 过渡 Demo / 高端型号 |
| C. Asterisk/FreePBX 二次开发 | FreePBX + 自研皮肤 | 快 | ★☆ | ★★ | 高（GPL，闭源分发需开源；模块许可需逐项确认） | 不推荐闭源销售 |
| D. PJSIP 商业库 | Teluu pjsua2 + 自研控制面 | 中 | ★★★★ | ★★★★ | 低（需购买商业授权） | 媒体质量不达标时的备选 |
| E. 纯 OEM/贴牌 | 第三方整机/软件 | 最快 | 取决于厂商 | ★ | 低 | 无法形成壁垒 |

### 3.1 为什么推荐 A（Go 自研）

- **单二进制 = 全平台**：`GOOS/GOARCH` 交叉编译，Windows/Linux/macOS/ARM 同一个代码库；前端 `go:embed` 进二进制，客户只需一个文件 + 一个数据目录。
- **零运行时依赖**：不用装 MySQL/Redis/Nginx/PHP；SQLite 内嵌，内存 100~300MB 起步，适合小主机和树莓派。
- **团队匹配**：公司已有 Go 服务端（alarmserver-go 等）与 Vue3 前端积累，学习和维护成本最低。
- **可控性**：呼叫路由、报警联动、录音存证等核心逻辑全部自有，方便做行业定制和白标。
- **许可证干净**：sipgo（BSD-2）、Pion（MIT）、Vue/Element Plus（MIT）均可闭源商用。

### 3.2 为什么 B/C 在"全平台"上会翻车

- FreeSWITCH 官方虽提供 Windows 构建，但生产环境普遍以 Linux 为主，Windows 上的服务化、性能、模块完整性都弱；安装包动辄数百 MB，还要带一堆 DLL。
- Asterisk 在 Windows 上没有官方原生支持（只能 WSL/虚拟机），与"客户给一台 Windows 小主机"的场景直接冲突。
- 两者都依赖"配置文件 + 重载"的运维模型，做 Web 化管理要么走 ARI/ESL 外挂，要么生成配置再 reload，状态一致性很难做好。
- 我们已经在 ZYCOO 上踩过一次：Asterisk + host 网络 + 重型依赖，在 macOS 开发机和 Docker Desktop 上直接不可用。

> **务实建议**：如果老板要求"3 个月内必须有一个能演示的完整 PBX"，可以先用 FreeSWITCH 做一版 Demo 接住需求，同时启动 Go 版自研；但**不要**把 FreeSWITCH 当作最终交付形态。

## 4. 推荐架构

### 4.1 总体架构

```text
┌ 单个可执行文件（Go + go:embed 前端）
│
├─ 接入层     Web UI (Vue3) · REST API · WebSocket · CLI/服务封装
├─ 业务层     拨号规则 · 前转 · 振铃组 · 队列 · IVR · 语音信箱 · 会议 · 广播 · 报警
├─ 呼叫控制   B2BUA 状态机 · fork · 转移 · 保持 · 代答 · 停泊 · 强插
├─ 媒体       RTP/RTCP/SRTP · 混音 · 放音 · 录音 · DTMF · 转码 · 抖动缓冲
├─ 传输       UDP / TCP / TLS / WS / WSS · IPv4/IPv6 · DNS SRV · NAT/ICE
└─ 数据       SQLite（配置/话单/留言） · 文件（录音/提示音/证书） · 日志/指标/抓包/诊断包

外部：SIP 话机 · 报警/对讲设备 · SIP 网关 · 运营商中继 · WebRTC 浏览器 · 第三方平台（Webhook/MQTT）
```

### 4.2 模块职责

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| `transport` | UDP/TCP/TLS/WS/WSS 监听、连接管理、DNS SRV/NAPTR、IPv6 | 端口复用、连接数限制、TLS 证书热加载 |
| `sipcore` | 事务、对话、消息编解码、重传、超时 | 基于 sipgo 封装，隔离其 API 变动 |
| `registrar` | 位置服务、多联系人、过期、NAT 探测、保活 | received/rport、Outbound、注册风暴限流 |
| `auth` | Digest（MD5/SHA-256）、中继 IP 鉴权、账号锁定 | 防暴力破解、nonce 管理 |
| `routing` | 拨号规则、路由群、中继选择、主叫改写、时间条件、黑名单 | 可测试的规则引擎，支持导入导出 |
| `call` | B2BUA 状态机、fork、保持、转移、代答、停泊、强插 | 状态机可回放，便于排障 |
| `media` | RTP 中继、对称 RTP/锁存、SRTP/DTLS、转码、抖动缓冲、放音、录音、DTMF、混音 | 先做中继，按需终止媒体 |
| `apps` | IVR、自动话务员、语音信箱、会议、队列、振铃组、广播、回呼 | 每个业务独立可插拔 |
| `store` | SQLite、迁移、CDR、录音索引、配置版本 | WAL、批量写、备份/恢复 |
| `api` | REST/OpenAPI、WebSocket 事件、RBAC、审计 | 与前端契约先行（OpenAPI 生成） |
| `provision` | 话机/设备模板、自动配置、与 `sip_web` 打通 | 支持 Yealink/Grandstream/Fanvil 及自家设备 |
| `ops` | 日志、指标、SIP 抓包、呼叫跟踪、诊断包、升级 | 一键导出、脱敏 |

### 4.4 关键设计决策

1. **Relay-first（先中继，后终止）**：两端编码一致时只转发 RTP，不做解码/混音/AEC，CPU 几乎为零，音质无损；只有 IVR/录音/会议/转码才终止媒体。这是控制复杂度、保证音质的关键。
2. **无 cgo**：全静态编译，交叉编译、代码签名、客户机器免运行库都简单。代价是 Opus 编码需规避（见 4.6）。
3. **SQLite 内嵌**：客户现场不装数据库；配置/话单/留言索引一个文件，备份=打包数据目录。CDR 批量提交，避免写放大。
4. **前端 `go:embed`**：发布物是一个 exe/二进制 + 一个数据目录；升级只替换二进制。
5. **服务化**：Windows 服务（`x/sys/windows/svc`）、systemd、launchd 三套封装，同一份业务代码。
6. **安全默认**：默认拒绝匿名呼叫；中继必须显式配置；Web 首次启动强制改密；登录失败自动封禁；外呼目的前缀白名单 + 并发上限（防 toll fraud）。
7. **可观测性内建**：每通呼叫保存信令 ladder、可导出 pcap、一键诊断包（配置+日志+抓包+系统信息，自动脱敏）。
8. **许可与容量**：Ed25519 离线授权文件，绑定机器指纹，按分机数/并发数分级；试用 30 天。早期可先不做，但数据模型要预留。

### 4.5 关键流程

**（1）设备注册**
`REGISTER`（Digest）→ 校验 → 记录 Contact + received/rport + 过期 → `200 OK` → 服务端 30s OPTIONS/CRLF 保活 → NAT 后设备保持在线。

**（2）一键报警（行业核心链路）**
设备按报警键 → `INVITE 8000`（报警短号，可带 Alert-Info/自定义头）→ 服务器识别为报警呼叫 → 查值班表 → 并行 fork 坐席（SIP 分机 + WebRTC 坐席 + 手机）→ 首个应答接听、其余 CANCEL → RTP 中继 + 录音 → WebSocket 推送弹屏（主叫、位置、摄像头流地址）→ 挂机写 CDR + 录音索引 + Webhook/MQTT 通知报警平台 → 若 30s 无人接，按升级链转下一级/短信。

**（3）外线呼入**
运营商中继 `INVITE` → IP/账号鉴权 → DID 匹配 → 路由到 IVR/自动话务员/振铃组/分机 → 呼叫中继出局时做主叫号码改写。

**（4）WebRTC 坐席**
浏览器 `WSS` → SIP over WebSocket → SDP（ICE + DTLS-SRTP）→ 服务端 Pion PeerConnection → 音频用 PCMU/PCMA 免转码（Chrome/Edge 可），必要时 TURN 中继。

### 4.6 编解码策略（重要）

| 场景 | 策略 |
| --- | --- |
| SIP 话机/报警设备 | G.711（PCMU/PCMA）必选；G.722 可选；**不做 G.729**（专利+复杂度） |
| 录音/IVR/会议 | 统一解码为 PCM16 8kHz 内部格式，处理完再编码 |
| WebRTC | 优先协商 PCMU/PCMA，避免 Opus 转码；Safari 兼容性需实测，必要时仅在 x86_64 构建启用 cgo Opus |
| 视频 | H.264 透传为主；调度台观看走 WebRTC/RTSP 旁路，不在 SIP 媒体面转码 |

> 纯 Go 的 Opus 编解码不完整，cgo 会破坏"全平台交叉编译"。**能用 G.711 解决的就不要引入 Opus 转码**，这是本项目最重要的工程取舍之一。

### 4.7 数据模型（核心表）

`extension`（分机）、`trunk`（中继）、`dial_rule`（拨号规则）、`route_group`（路由群）、`group` / `group_member`（振铃组/队列/代答组）、`ivr` / `ivr_node`、`prompt`（提示音）、`voicemail`、`conference`、`cdr`、`recording`、`contact`（注册位置）、`user` / `role` / `audit_log`、`setting`、`license`、`alarm_policy`（行业）。

```text

├── internal/

│   ├── auth/               # Digest / ACL / 封禁
```

## 5. 全平台交付方案

| 平台 | 交付形态 | 安装/自启 | 关键注意点 |
| --- | --- | --- | --- |
| **Windows 10/11/Server 2016+**（x64/arm64） | 单 exe + 安装包 + 托盘程序 | Inno Setup；注册为 Windows 服务；自动加防火墙入站规则 | UDP 收包缓冲区调大；Defender 排除数据目录；服务账户权限；首次配置向导 |
| **Linux x86_64 / arm64** | deb / rpm / tar.gz | nfpm 打包；systemd unit；`CAP_NET_BIND_SERVICE` | `ulimit -n`、时区、SELinux/AppArmor、日志轮转 |
| **macOS 12+**（Intel/Apple Silicon） | .pkg + LaunchDaemon | pkgbuild/productbuild；签名 + 公证 | macOS 15+ 本地网络权限提示；不要依赖 Docker host 网络；适合开发/演示与小规模 |
| **树莓派 / ARM 盒子** | arm64/armv7 tar/deb | systemd | 低内存配置档；SD 卡写放大（录音写外置盘）；性能按 50~100 分机设计 |
| **Docker** | 单镜像（distroless） | `docker compose` | 固定 RTP 端口段映射；`--network host` 仅 Linux 可用；**macOS/Windows Docker Desktop 不支持 host 网络**，需配 `EXTERNAL_IP` + 端口段 |
| **云主机** | 单机/双机冷备 | 同上 | 公网 IP/1:1 NAT 的 SDP 地址配置；安全组；TLS；防扫描（5060 暴露必被扫） |

**统一原则**：客户拿到的是一个安装包 + 一个 Web 地址；安装完浏览器打开 `https://IP` 走完向导（网络 → 证书 → 分机 → 中继 → 测试呼叫）即可使用。

**资源参考**（G.711 中继、无转码）：

| 规模 | CPU | 内存 | 带宽 | 存储（录音） |
| --- | --- | --- | --- | --- |
| 50 分机 / 25 并发 | 2 核 | 2 GB | 10 Mbps | 1 路约 28 MB/小时 |
| 200 分机 / 100 并发 | 4 核 | 4 GB | 50 Mbps | 按并发 × 时长估算 |
| 500 分机 / 250 并发 | 8 核 | 8 GB | 100 Mbps | 建议独立数据盘 |

### 8.2 产品化清单（容易被忽略）

- **迁移工具**：从 miniSIPServer/其他 PBX 导入分机、中继、拨号规则（CSV/Excel）。
- **自动配置**：话机与自家设备上电即配（DHCP Option 66 / 配置 URL / TR-069 可选）。

- **支持包**：配置（脱敏）+ 日志 + 最近 N 通呼叫 pcap + 系统信息，一键下载。
- **多语言**：简体/繁体/英文（与 `sip_web` 的 i18n 体系一致）。
- **文档**：安装、开局、话机配置、故障排查、API 文档，配套视频。

## 9. 两周 PoC 计划（可立即启动）

> **已完成的技术预验证（2026-11-16）**：Go 1.24.3 + sipgo **v1.7.3** 编译运行通过，UDP 监听（冒烟端口 15060），收到 REGISTER 后正确返回 `200 OK`，并自动回填 `received` / `rport`（NAT 场景的关键字段）。验证代码约 20 行，见 [`poc/sipgo-smoke/`](../poc/sipgo-smoke/)。结论：协议栈选型可用；剩余不确定性集中在**媒体、NAT、真实设备互通**，因此 PoC 的重点应放在 D5~D9。

| 天 | 内容 | 产出 |
| --- | --- | --- |
| D1~D2 | 搭 Go 骨架、sipgo 跑通 UDP 监听、Web 登录页 | 可运行二进制 |
| D3~D4 | REGISTER + Digest 鉴权 + 位置服务 + 保活 | 软电话注册成功 |
| D5~D6 | INVITE/BYE 转发（B2BUA）、SDP 协商、RTP 中继 | 两路软电话互通语音 |
| D7 | 录音（双向 WAV）、CDR 落库 | 通话结束可回放、可查话单 |
| D8 | Web 面板：注册列表、活动呼叫、话单、录音下载 | 浏览器可见 |
| D9 | 真实报警设备接入（改服务器地址→注册→呼叫） | 设备侧端到端 |
| D10 | 三平台交叉编译 + Windows 服务/安装包雏形 + 演示 | 演示 + 评估结论 |

**PoC 验收标准**：

1. 2 款软电话 + 1 台真实报警设备同时注册在线；
2. 设备呼叫坐席，双向语音清晰，无单通；
3. 通话自动录音，Web 可回放，话单含主叫/被叫/时长/结果；
4. Windows、Linux、macOS 三个平台各出一个可运行产物；
5. 拔掉网线 30 秒再插回，设备 60 秒内自动恢复注册。

> PoC 只验证"技术链路 + 真实设备"，不追求功能完整；两周后给出"继续/调整/放弃"的明确建议。
